After a call, here is how to tell what happened and whether it went well.

Every phone call becomes one review in LangSmith. It is written to be read top to bottom: a one-line headline, a short summary, what to check, a scorecard, the call turn by turn, then speed, waiting cues, booking and cost. The technical evidence stays underneath for the day you need it.

Open LangSmith

Sign in to your workspace and open the project servicevoice-call-reviews. The dashboard is called ServiceVoice · call quality; the listening queue is ServiceVoice calls to review. Runtime traffic (one span per model request) lives in servicevoice-runtime and is not a call review.

Your routine after a call

  1. Wait a minute or two, then open the project. The newest row named voice.call.review is your call. Its Input column already shows the headline, for example Inbound phone call · 3 min 49 s · 13 caller turns · 1 appointment saved · ended: assistant hung up after the goodbye · checks clear.
  2. Read 1 Summary. Two or three lines say what happened, which tools ran, how many cues played, the average delay and how the call ended. What to check tells you exactly where to look if anything is flagged.
  3. Scan 2 Scorecard. Every check is a plain question with PASS, FAIL, UNCERTAIN or N/A and a one-phrase reason. Only FAIL and UNCERTAIN deserve your time.
  4. Follow 3 Turn-by-turn timeline. One sentence per caller turn: when they spoke, whether a cue played, when the real answer or tool call started, which tools ran, and the delay Vapi measured before the first audio.
  5. Expand the trace when you want the mechanics: one turn NN row per caller turn with its cue, gemini request and tool rows, plus the speech synthesis and vapi groups.
  6. If the call is in the listening queue, open it there, play the recording in the Vapi dashboard (Inputs → vapi_call_url) and answer the five rubric questions. Your answers become human_* feedback beside the automatic checks.
Two flags, two meanings. needs_review = 1 means a conversation, booking or evidence check failed or stayed uncertain. slow_call = 1 means a speed target was missed. A slow but correct call is not a conversation problem, and vice versa.

Scores

1 = pass
0 = fail
blank = uncertain or not applicable

The value column says which of the two blank cases it is.

Flags

needs_review and slow_call: 1 means look. coverage_semantic_review, coverage_provider_log and assistant_hung_up describe the review itself, not the agent.

Measurements

Every metric_* row is a number, not a score: milliseconds, counts, dollars or a confidence between 0 and 1. Lower delay is better; more cues are not automatically better.

Code checks on saved records always win over the reviewer: a failed booking_integrity turns booking_accuracy into a fail, and missing evidence blocks every pass.

Reading one turn

Turn 7 · caller spoke at 1:42.3 for 2.1 s · cue "Let me check that." at 0.58 s · tool call search_availability after 2.16 s on the server · tool search_availability ok 0.05 s · first audio 1.03 s after the caller stopped (Vapi) · assistant spoke for 6.2 s
  • caller spoke at … for … comes from Vapi's speech segments. A low recognition confidence is called out here; it is the most common reason a name or number is wrong.
  • cue … at … is the server time from the gateway request to the cue audio being yielded. no cue: caller gave private details explains a deliberate silence.
  • tool call … after … or spoken answer after … is when the real reply started on the server; speech synthesis and the phone network add to what the caller hears.
  • first audio … after the caller stopped (Vapi) is Vapi's stage sum for that turn. It is attached only when Vapi and the gateway counted the same number of caller turns; join_basis says so.
  • speculative request(s) cancelled are requests Vapi started while the caller was still talking and then discarded. They cost tokens, not caller time, and any cue they held is refunded.

The dashboard

ServiceVoice · call quality starts with a text block repeating the legend, then tiles: calls reviewed, needs-a-human-look fraction, slow-call fraction, bookings saved, the six quality pass rates, average first response, slowest answer start, reviewer coverage and provider cost. Below them, lines show response time over time and where the first response goes, and bars show cues per call, how calls ended, and interruptions and recognition confidence.

Every chart filters on voice.call.review rows of the current contract, so reviewer status rows and runtime spans never dilute a call average. Pass rates average 1/0 scores over calls where the check applied; a perfect tile over three calls is three calls, not a benchmark. Recreate or update the dashboard with python -m evals.langsmith_dashboard --apply; it also creates the listening queue and renames older sections with an Archive · prefix.

The listening queue

Automatic checks never hear audio. Calls flagged needs_review are added to the annotation queue once. For each item: listen in Vapi, read the review, then answer sounded natural, cues well timed, heard correctly, booking correct and overall acceptable with 1 or 0, leaving a question blank if you could not tell. These become human_* feedback on the same run, so the dashboard can later compare automatic and human verdicts. A queue outage never blocks a review; the worker's status reports human_review_queue counts.

The three evaluation layers

Offline tests2,400+ unit, contract, browser and fault tests on disposable data. Run by python -m evals.offline and in GitHub Actions.
Synthetic experimentsAuthored reference conversations through the real gateway in disposable schedulers, judged by code and an advisory Gemini judge, stored as LangSmith datasets and experiments.
Real-call reviewsThis guide. Every production call, reviewed automatically and queued for a human listen when flagged.

Passing one layer does not establish the next. Text response time is not acoustic latency, and a matching receipt does not prove spoken consent.

What a review cannot prove

  • What the caller actually heard, pronunciation, naturalness or background noise. Server times are not phone playback.
  • That a waiting cue reached the phone before the answer did.
  • Consent beyond the stored text and the order of turns.
  • Anything about calls the reviewer could not fetch: check voice.review.coverage (tagged reviewer-status) when a call seems to be missing.
